# 1. Introduction

## 1.1 What Code-Genius is

**Code-Genius** is an internal AI assistant for technical work. A user opens a conversation in the Code-Genius web UI, asks a question (write or fix code, translate SAS to ANSI SQL, analyse data, review a UI, and so on) and gets an answer generated by a Large Language Model (LLM). Users can also upload their own files into a conversation, and the assistant then answers with those files as context.

This repository contains only the **backend**: a Python **FastAPI** service that sits between the web UI and the systems that do the heavy lifting. It does not contain the web UI, the LLM, the database or the file store; it talks to all of those over HTTP.

## 1.2 What the backend is responsible for

- Checking that every request comes from a signed-in user (it validates a JWT issued by the organisation's SSO/auth service).
- Keeping each user's **conversations** and **messages** in the database, and making sure users can only see their own.
- Accepting **document uploads** (.txt, .csv, .docx, .xlsx), extracting their text, checking they are not too large for the LLM, and storing them in Ozone object storage.
- Building the prompt for every question: system prompt + uploaded documents + as much earlier conversation as fits + the new question, all measured in LLM tokens.
- Calling the LLM (normally or as a live stream) and saving the answer.
- Export, rename and delete of conversations; delete of single messages; download of uploaded files.
- Structured logging, including a separate log of every LLM call for usage tracking.

## 1.4 Glossary

| Term | Meaning in this project |
|---|---|
| Conversation | One chat thread owned by one user. Has an ID (UUID), a title and timestamps. Stored in table `CD_CONVERSATIONS`. Sometimes called a "session" in the code; it is not the login session. |
| Message | One user question or one assistant answer inside a conversation. Stored in `CD_MESSAGES`. |
| Document | A file uploaded into a conversation. Metadata in `CD_DOCUMENTS`; the file itself and its extracted text in Ozone. |
| LLM | Large Language Model. Reached through an OpenAI-compatible HTTP API at `LLM_BASE_URL`. |
| Token | The unit an LLM reads and writes (roughly ¾ of a word). All size limits in this system are counted in tokens. |
| Context window | The maximum number of tokens the LLM accepts in one call (prompt + answer). Configured as `LLM_CONTEXT_LIMIT_TOKENS`. |
| Tokenizer service | A separate HTTP service that counts tokens exactly as the LLM would. |
| Ozone | Apache Ozone object storage, reached through an internal REST wrapper. Holds uploaded files, extracted text and archived logs. |
| Database service | An internal REST wrapper around Teradata. The backend sends it SQL text plus named parameters. |
| JWT | JSON Web Token. A signed token proving who the user is; sent as `Authorization: Bearer <token>`. |
| SSE | Server-Sent Events. The format used by the streaming chat endpoint to push the answer word by word. |
| UAT / PROD | The two server environments. The start script picks one from the host name. |

# 3. High-Level Architecture

## 3.1 Component overview

The backend is a single stateless FastAPI application. All state lives in external systems, so several instances can run side by side behind a load balancer. The picture below shows the main pieces.

![Figure 1 – Code-Genius backend and the systems it depends on](images/arch.png)

The code is layered in the usual FastAPI way:

- **Routers** (`app/api/routers`) define the URLs. They check the user, validate input with Pydantic **schemas** (`app/api/schemas`) and call a service.
- **Services** (`app/services`) hold the business logic: chat orchestration, document processing, token counting, summarisation and authentication.
- **Clients** inside the services talk to the outside world: `DatabaseClient` (database service), `OzoneClient`/`httpx` (Ozone), `AsyncOpenAI` (LLM) and `httpx` (tokenizer).
- **Cross-cutting** modules: `config.py` (settings from `.env`), `prompt_manager.py` + `prompts.yaml` (system prompt) and `logger.py` (logging).

## 3.2 Technology stack

| Area | Technology | Used for |
|---|---|---|
| Language / runtime | Python 3.10+ (uses the newer union type-hint syntax), Conda environments on the servers | Everything |
| Web framework | FastAPI, Starlette, Uvicorn (ASGI server) | HTTP API, middleware, SSE streaming, OpenAPI docs at `/docs` |
| Validation / settings | Pydantic v2, pydantic-settings | Request/response models; loading `.env` |
| Auth | python-jose | Verifying JWT signatures and expiry |
| HTTP client | httpx (async) | Calls to database service, Ozone and tokenizer |
| LLM SDK | openai (`AsyncOpenAI`) | Chat completions against any OpenAI-compatible server |
| File parsing | pandas + openpyxl (xlsx), python-docx (docx), csv (stdlib) | Text extraction from uploads |
| Config files | PyYAML | Loading `prompts.yaml` |
| Database | Teradata, via an internal REST "database service" | Conversations, messages, document metadata |

## 3.3 External systems and how they are called

| System | Config keys | Calls made by the backend | Called from |
|---|---|---|---|
| SSO / auth service | `EXTERNAL_JWT_SECRET`, `EXTERNAL_JWT_ALGORITHM` | None. The backend only verifies tokens the auth service has issued, using the shared secret. | `AuthService` |
| LLM | `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | `chat.completions.create` (normal and `stream=True`); temperature 0.0 for answers, 0.3 for summaries. | `ChatService`, `SummarizationService` |
| Tokenizer | `TOKENIZE_SERVICE_URL`, `TOKENIZE_SERVICE_MODEL`, `TOKENIZE_TIMEOUT_SECONDS` | `POST <url>` with `{model, prompt, add_special_tokens: true, return_token_strs: false}`; reads `count` from the reply. | `TokenService` |
| Database service | `DATABASE_SERVICE_URL`, `DB_SCHEMA` | `POST /teradata/query` (SELECT) and `POST /teradata/mutation` (INSERT/UPDATE/DELETE) with `{sql, params}`. Named parameters only (`:name`). Replies contain `rows` (list of lists). | `DatabaseClient`, `TeradataClient` |
| Ozone | `OZONE_SERVICE_URL`, `OZONE_BUCKET_ID` | Upload: `POST /ozone/buckets/{bucket}/objects` (multipart `file`). Download: `GET /ozone/buckets/{bucket}/objects/download?path=<name>`. | `OzoneClient`, `ChatService`, `document_router`, `logger` |

> **Watch out:** The tokenizer is on the critical path. If it is down, uploads and chat both fail: `TokenService.count_tokens` raises instead of estimating, even though a `TOKENIZE_FALLBACK_ENABLED` setting exists.

## 3.4 Data model

The backend owns three tables in the Teradata schema named by `DB_SCHEMA`. There are no migration scripts in the repository; the columns below are what the SQL in the code reads and writes.

### CD_CONVERSATIONS – one row per conversation

| Column | Meaning |
|---|---|
| CONV_ID | Primary key. UUID generated by the backend. |
| USER_ID | Owner. The `user.username` claim from the JWT. Used for every ownership check. |
| CONV_TITLE | Title. Starts as "New Conversation", replaced by the first five words of the first question, or renamed by the user. |
| CREATED_TIME | Set on insert. |
| UPLOADED_TIME | Used as "last updated". Set on insert and when the auto-title is set. Conversations are listed newest first by this column. |

### CD_MESSAGES – one row per question or answer

| Column | Meaning |
|---|---|
| MESSAGE_ID | Primary key. UUID. |
| CONVERSATION_ID | Foreign key to `CD_CONVERSATIONS.CONV_ID`. |
| MSG_ROLE | `user` or `assistant`. |
| MSG_CONTENT | The text. |
| MSG_TIMESTAMP | Set on insert; history is ordered by it. |
| TOKEN_COUNT | Tokens in the message, counted on save. |

### CD_DOCUMENTS – one row per uploaded file

| Column | Meaning |
|---|---|
| DOC_ID | Primary key. UUID. |
| CONVERSATION_ID | The conversation the file belongs to. |
| DOC_NAME | Original file name. Also used as the Ozone object name when reading or downloading (see 9.1). |
| DESCRIPTION | Currently always NULL. The chat code looks for an `EXTRACTED_TEXT_KEY:` marker here that upload never writes (see 9.1). |
| DOC_TYPE | Extension without the dot: txt, csv, docx, xlsx. |
| OZONE_BUCKET_NAME / OZONE_KEY_NAME | Bucket and a key of the form `<conversation_id>_<filename>`. |
| SIZE_BYTES | Size of the original file. |
| DOC_LANGUAGE | Always NULL (reserved). |
| UPLOADED_BY / UPLOADED_TIME | Uploader user ID and time. |
| TOKEN_COUNT | Tokens in the extracted text. |

Relationships: one conversation has many messages and many documents. Deleting a conversation deletes its message and document rows first, then the conversation row.

## 3.5 Request flow: asking a question

This is the most important flow in the system. `POST /api/chat/ask` and `POST /api/chat/stream` both follow it; the streaming version sends the answer as it is generated instead of at the end.

1. **Authenticate.** `AuthService.get_current_user_info` reads the Bearer token, verifies signature and expiry, and returns the user ID and name.
2. **Find or create the conversation.** If no `conversation_id` was sent, a new UUID is generated and a `CD_CONVERSATIONS` row is inserted.
3. **Set the title** from the first five words of the question, if the conversation still has the default title.
4. **Save the user's question** in `CD_MESSAGES` (its token count is measured first).
5. **Load documents.** All `CD_DOCUMENTS` rows for the conversation are read and each file's content is downloaded from Ozone. They are joined as `Document: <name>` blocks separated by `---`.
6. **Calculate the token budget** (figure 2). The tokenizer counts the system prompt, the documents and the question. Together with the fixed safety buffer and the space reserved for the answer, this gives the **history budget**. If the fixed parts alone are larger than the context window the request fails with "Input too long".
7. **Select history.** Earlier messages are taken newest-first while they fit. A message that does not fit, and is longer than `SUMMARY_THRESHOLD_TOKENS`, is summarised by the LLM and the summary is used if it fits. Selection stops at the first message that still does not fit. The result is cleaned so roles alternate and it starts with a user message.
8. **Build the prompt:** `[system prompt + documents] + [selected history] + [question]`.
9. **Call the LLM** with temperature 0.0 and `max_tokens = RESPONSE_RESERVED_TOKENS`.
10. **Save the answer** in `CD_MESSAGES`, write an entry to the LLM log, and return the answer, title, message ID and token usage.
11. **On failure** the saved question is deleted again, and if the conversation was created by this request it is deleted too, so a failed first question leaves nothing behind.

## 3.6 Request flow: uploading documents

1. **Authenticate** the user.
2. **Conversation:** if no `conversation_id` is given, create a new conversation (title "New Conversation").
3. **Extract text** from every file one by one (`TextCombiner`). Unsupported or unreadable files are marked FAILED but do not stop the others. If every file fails, the request stops here.
4. **Count tokens** of all extracted text combined (one tokenizer call).
5. **Check the limit:** combined tokens must be ≤ `LLM_CONTEXT_LIMIT_TOKENS × DOCUMENT_UPLOAD_FAIL_THRESHOLD_PERCENT / 100`. If not, **all** files in the batch are rejected and nothing is stored.
6. **Store each file in parallel** (max 5 at a time): upload the original file and an extracted-text copy (`<document_id>.txt`) to Ozone, then insert the `CD_DOCUMENTS` row.
7. **Return a summary** with per-file results, the token count and the limit.

> **Note:** The size check is per upload request. It does not add the tokens of documents uploaded earlier to the same conversation.

## 3.7 Security model

- **Authentication** is delegated. The backend never sees passwords. It trusts any JWT signed with `EXTERNAL_JWT_SECRET` using `EXTERNAL_JWT_ALGORITHM` that has not expired and contains a `user` object with a `username`.
- **Authorisation** is ownership-based: a conversation belongs to the `USER_ID` that created it, and a document or message belongs to whoever owns its conversation. Most endpoints check this; section 9 lists the ones that do not.
- **SQL injection**: all values are sent as named parameters. The only value placed directly into SQL text is `DB_SCHEMA`, which `config.py` restricts to a plain identifier.
- **Transport**: HTTPS is enabled when `SSL_KEYFILE` and `SSL_CERTFILE` are set. CORS is limited to `BACKEND_CORS_ORIGINS`.
- **Secrets** live only in `envProd` / `envDev` on the servers. They are git-ignored and copied to `.env` at deploy time.

## 4.1 Conventions used across the code

- **Singletons.** `ChatService`, `TokenService`, `SummarizationService`, `DocumentTokenService` and `DatabaseClient` override `__new__` so there is one instance per process. Most also expose a module-level instance (`token_service`, `db_client`, …) that other modules import.
- **Dependency injection.** Routers get services through FastAPI `Depends(...)` (`get_chat_service`, `get_document_processor`, …) and the user through `Depends(AuthService.get_current_user_info)`.
- **Async everywhere.** All I/O uses `async`/`await`. CPU-heavy parsing of .xlsx and .docx is moved off the event loop with `asyncio.to_thread`.
- **Database results** come back as `{"rows": [[col1, col2, ...], ...]}`; code reads columns by position, so SELECT column order matters.
- **Request IDs.** Each handler builds a `req_<milliseconds>` ID and puts it in its log lines so one request can be followed through the log.

## 5.2 app/core/config.py – settings

Defines a single `Settings` class (pydantic-settings) and a global `settings` instance used everywhere. Values come from `.env` in the working directory or from real environment variables, which take priority. **No setting has a default**: if a key is missing, the app refuses to start and names the missing key. Keys are case-insensitive and unknown keys are ignored.

Validators run at start-up:

- `SECRET_KEY` must be at least 32 characters.
- `LLM_API_KEY` must not be empty.
- `DB_SCHEMA` must be a plain SQL identifier (letters, digits, underscore). This matters because it is pasted directly into SQL text.

The full list of settings is in section 7.2.

## 5.3 app/services/auth/auth_service.py – authentication

`AuthService` is a set of static methods. The class comment states the design: this backend is a **resource server**; it never issues tokens, it only checks tokens issued by the central auth service.

| Method | What it does |
|---|---|
| `verify_access_token(token)` | Decodes the JWT with `EXTERNAL_JWT_SECRET` and `EXTERNAL_JWT_ALGORITHM` (python-jose also checks `exp`). Any failure → HTTP 401 "Invalid or expired access token". |
| `extract_identity(payload)` | Expects `payload.user` to be an object. `user.username` becomes `user_id`; `firstname lastname` becomes the display `username` (falls back to the ID). Missing pieces → 401. |
| `get_current_user_info(request)` | The FastAPI dependency used by every protected endpoint. Reads `Authorization: Bearer <token>`, verifies it and returns `TokenData(username, user_id)`. Missing header → 401 "Missing access token". |
| `get_current_user(request)` | Same, but returns only the display name. Not used by the current routers. |

Expected token payload:

```
{
  "user": {
    "username":  "11111",          // becomes user_id (owner key in the DB)
    "firstname": "ABC",
    "lastname":  "XYZ",
    "email":     "abc.xyz@abc.com"
  },
  "exp": 1767014007                // expiry, seconds since epoch
}
```

## 5.4 app/api/routers/chat_router.py – chat endpoints

Thin HTTP layer over `ChatService`. Every handler takes the current user from `AuthService`, logs the request with a request ID and timing, calls the service, and maps the result to a schema. The endpoints themselves are documented in section 6.3.

| Function | What it does |
|---|---|
| `get_chat_service()` | Dependency returning the `ChatService` singleton. |
| `verify_conversation_ownership(conversation_id, user_id)` | Reads `USER_ID` of the conversation; returns True only if it matches. Used by export and rename to stop users acting on someone else's conversation (IDOR protection). |
| `ask_question` | `POST /ask`. Calls `process_message`, takes the assistant message ID from the last history entry, returns `ChatResponse`. **Errors are returned as HTTP 200 with the `error` field set**, not as an HTTP error status. |
| `stream_message` | `POST /stream`. Wraps `process_message_stream` in an SSE generator: a `metadata` event, then `chunk` events, then `complete`, and always a final `[DONE]`. |
| `export_chat` | `GET /export`. Ownership check, then `export_conversation`. |
| `get_chat_history` | `GET /history/{id}`. Uses the ownership-checked service call; 404 if not found or not owned. |
| `list_conversations` | `GET /conversations`. All conversations of the user, newest first. |
| `delete_conversation` | `DELETE /conversations/{id}`. 404 if not found or not owned. |
| `delete_message` | `DELETE /message/{id}`. 404 if not found or not owned. |
| `update_conversation_title` | `PUT /conversations/{id}/title`. Ownership check (403), then rename. |

Several handlers check `hasattr(chat_service, "...")` and fall back to older methods or return 501. With the current `ChatService` all methods exist, so the fallback branches are never taken.

## 5.5 app/services/chat/chat_service.py – chat orchestration

The largest and most important module (≈1,140 lines). `ChatService` is a singleton that holds an `AsyncOpenAI` client and implements everything to do with conversations, messages and LLM calls. The high-level flow is in section 3.5; the methods are grouped below.

### Conversation and message storage

| Method | What it does |
|---|---|
| `create_conversation_if_not_exists(conv_id, user_id, title)` | Returns the existing title, or inserts a new row and returns the given title. |
| `update_conversation_title_if_empty(conv_id, new_title)` | Sets the title only if it is empty or "New Conversation"; also bumps `UPLOADED_TIME`. |
| `update_conversation_title(user_id, conv_id, new_title)` | Unconditional rename (the router has already checked ownership). |
| `list_user_sessions(user_id)` | All conversations of a user, ordered by `UPLOADED_TIME` descending. |
| `save_message(conv_id, role, content, message_id=None)` | Counts tokens, inserts into `CD_MESSAGES`, returns the message ID. |
| `save_message_with_metadata(...)` | Wrapper around `save_message`. The extra arguments (`context_used`, `sources`, `dir`) are accepted but **not stored**, because those columns do not exist. |
| `_get_history(conv_id)` | All messages of a conversation in time order. **No ownership check** – internal use only. |
| `get_conversation_history(user_id, conv_id)` | Same, but returns `None` unless the user owns the conversation. Used by the API. |
| `get_conversation_owner` / `get_message_owner` | Look up the owner of a conversation, or of the conversation a message belongs to. |
| `delete_conversation(user_id, conv_id)` | Ownership check, then deletes messages, document rows and the conversation (in that order). Files in Ozone are **not** deleted. |
| `delete_message(message_id, user_id=None)` | Deletes one message; checks ownership when `user_id` is given. Also used internally for roll-back. |
| `export_conversation(conv_id, format)` | Builds a text (`Title` + `=====` underline) or Markdown (`# Title`, `**Role:**`) transcript. |

### Documents as context

| Method | What it does |
|---|---|
| `get_session_documents(conv_id)` | Reads `CD_DOCUMENTS` rows for the conversation. Tries to find an extracted-text key in `DESCRIPTION` after the marker `EXTRACTED_TEXT_KEY:`. |
| `download_document_content(ozone_key, txt_ozone_key)` | Downloads from Ozone (preferring the extracted-text key). If the text is a JSON list of `{text, metadata}` chunks it is re-assembled with `[Page n]` / `[Row n]` markers; otherwise the raw text is returned. Returns "" on any error. |

### Token budget and history selection

| Method | What it does |
|---|---|
| `_get_history_with_budget(conv_id, budget, mode, exclude_last_user_message)` | Loads history, drops the question that was just saved (so it is not counted twice), removes any `system` rows and calls `_select_history_messages`. Returns the messages and a decision log. |

Keeps a message if it fits; otherwise tries an LLM summary if the message is over the summary threshold; otherwise stops. Then fixes role alternation and makes the list start with `user`. ### LLM calls

| Method | What it does |
|---|---|
| `generate_response(conv_id, user_message, user_id)` | The full pipeline from section 3.5 for a normal (non-streaming) answer. Returns `response`, `title`, `token_usage` (system, doc, history, query, input, output, total tokens) and `history_decisions`. Rolls back the user message on any error. |

| `process_message_stream(...)` | Public entry for `/stream`: yields `{chunk, is_complete: false}` items, then one `{is_complete: true, full_response, sources: []}`, or `{error}`. |

# 6. API Details

## 6.1 General conventions

- **Base URL**: `http(s)://<host>:9002`. HTTPS when SSL files are configured.
- **Interactive docs**: `/docs` (Swagger UI) and `/redoc` are generated by FastAPI and always match the running code.
- **Authentication**: all endpoints except `GET /` require `Authorization: Bearer <JWT>`. Missing or bad tokens give **401** with `{"detail": "..."}`.
- **Content types**: JSON for chat; `multipart/form-data` for upload; `text/event-stream` for streaming; `application/octet-stream` for download.
- **Errors** use FastAPI's standard shape `{"detail": "message"}`, except `POST /api/chat/ask` (errors in the body with HTTP 200) and `POST /api/documents/upload` (status in the body, see 6.4).
- **Validation errors** (missing or wrongly typed fields) give **422** with FastAPI's standard error list.
- **IDs** are UUID strings.

```
}
```

**Example response**

```
{
  "response": "Here is the ANSI SQL version ...",
  "conversation_id": "5b0c1c8e-7a3d-4e3f-9d0e-2f7c1a9b4e11",
  "title": "Convert this SAS PROC SQL...",
  "message_id": "a3f9...",
  "sources": [],
  "token_usage": {

  },
```

**Errors**

| Status | When |
|---|---|
| 200 + `error` | Any processing failure (LLM down, tokenizer down, input too long, database error). `response` is null, `title` is "Error", `error` holds the message. For a new conversation `conversation_id` is null because it was rolled back. |

Same as `/ask`, but the answer is sent as Server-Sent Events while it is generated, so the UI can show it word by word.

| Item | Detail |
|---|---|
| Method / path | `POST /api/chat/stream` |
| Authentication | Bearer JWT in the `Authorization` header (see 7.1) |

```
  "successful_files": ["schema.docx", "sample.csv"],
  "failed_uploads": 0,
  "failed_files": [],
  "results": [
    {"document_id": "d1...", "filename": "schema.docx", "status": "SUCCESS",
     "processing_time_sec": 0.84, "message": "Document uploaded sussessfully"},
    {"document_id": "d2...", "filename": "sample.csv", "status": "SUCCESS", ...}
  ],
  "token_validation": {"is_valid": true, "token_count": 5321, "token_limit": 24000},
  "extraction_details": [
    {"filename": "schema.docx", "text_length": 18342, "status": "SUCCESS"},
    {"filename": "sample.csv",  "text_length": 4410,  "status": "SUCCESS"}
  ],
  "error": null
}
```

**Errors**

| Status | When |
|---|---|
| 200 with `stage` = `Token_validation_failed` | Batch is over the token limit. Nothing is stored. `error` holds `aggregate_tokens`, `threshold_tokens`, `percentage_used` and a user-friendly `error_message`. |
| 200 with a file `status` = `FAILED` | Individual files that failed to store are listed in `failed_files` / `results`. |
| 401 | Missing or invalid token. |
| 422 | No `files` field. |
| 500 | If **every** file fails text extraction the handler currently crashes instead of returning the intended `stage: "EXTRACTION"` response (see 9.2). |

> **Note:** Always check `successful_uploads`, `failed_files` and `stage` in the body; the HTTP status is 200 even when nothing was stored.

> **Note:** `token_limit` = `LLM_CONTEXT_LIMIT_TOKENS × DOCUMENT_UPLOAD_FAIL_THRESHOLD_PERCENT / 100`. The 24000 in the example is only an illustration.

## 6.5 Authentication endpoints (inactive)

`auth_router.py` defines `POST /login` (form field `token`, sets cookie `codegenius_access_token`, returns `Token`), `POST /logout` (clears the cookie) and `GET /session` (returns `{user, user_id}`). These routes are **not reachable**: the router is not mounted in `main.py`, and the login handler calls methods that `AuthService` no longer has. Authentication today is header-only (section 3.7). Either delete this file or rebuild it on purpose; do not just mount it.

# 7. Configuration

## 7.1 How configuration works

- All settings are read by `app/core/config.py` from a file named `.env` in the directory the app is started from.
- A real environment variable with the same name overrides `.env` (`start.sh` uses this to force `PORT=9002`).
- Every key is mandatory. A missing key stops start-up with a "Field required" error naming it.
- On the servers, `start.sh` copies `envProd` (PROD) or `envDev` (UAT) over `.env` on every start, keeping one backup as `.env.bak`. **Edit `envProd` / `envDev`, not `.env`**, or your change will be lost on the next deploy.
- None of these files are in git. Ask the current owner for the values and keep them in the team's secret store.

# 8. Deployment and Operations

## 8.1 Environments

| Environment | Host | Conda environment | Config file |
|---|---|---|---|
| PROD | `sal25189077` | `/data0/anaconda3-new/envs/brcm_env_prod` | `envProd` |
| UAT | `sal25188480` | `/data0/anaconda3-new/envs/brcm_v2` | `envDev` |
| Any other host | – | UAT settings (with a warning) | `envDev` |

Defaulting unknown hosts to UAT is deliberate: a wrong UAT start is a failed start, but a wrong PROD start would point an unknown machine at production data.

## 8.2 Deploying with start.sh

Copy the code to the server, make sure `envProd` or `envDev` is in the same folder, then run:

```
bash start.sh
```

The script:

1. Detects the environment from the short, lower-cased host name.
2. Checks `main.py` and the Conda environment exist.
3. Copies the right env file to `.env` (backing up the old one to `.env.bak`).
4. Creates `logs/` and `run/`.
5. Stops the previous instance: the PID in `run/server.pid` plus any `uvicorn main:app … --port 9002` process; waits up to 15 s, then kills.
6. Refuses to start if something else still holds port 9002.
7. Activates Conda and starts `python -m uvicorn main:app --host 0.0.0.0 --port 9002` (adding SSL options if both SSL paths are set and exist), detached with `setsid nohup`, output to `logs/stdout.log`.
8. Polls `GET /` over HTTPS then HTTP every 3 s for up to 2 minutes. Prints OK and exits 0 on success; otherwise prints the last 30 lines of `logs/stdout.log` and exits 1.

## 8.4 Logs and troubleshooting

| Where | What is in it |
|---|---|
| `logs/stdout.log` | Everything Uvicorn prints, including start-up errors such as a missing setting. Look here first if the service does not start. |
| `logs/app.log` (+ `.1` … `.10`) | Application log in JSON. Search by `req_...` ID, user ID (`uid`) or conversation ID (`conv`). |
| `logs/llm.log` | One entry per LLM call: model, prompt/completion tokens, duration, success or error, start of prompt and answer. |
| Ozone `logs/YYYY-MM-DD/` | Rotated logs, gzip-compressed. |

| Symptom | Likely cause and check |
|---|---|
| Service will not start, "Field required" | A key is missing from `envProd`/`envDev`. The message names the key. |
| Every request 401 | `EXTERNAL_JWT_SECRET` / `EXTERNAL_JWT_ALGORITHM` do not match the auth service, or tokens have expired. |
| Chat and uploads both fail | Tokenizer service down or wrong `TOKENIZE_SERVICE_URL`. Look for "External tokenization service failed". |
| 503 "Database service error/unavailable" | Database REST service down or SQL error; details are in `app.log`. |
| "Failed to generate response from LLM service" | LLM endpoint, key or model name wrong or unavailable; see `llm.log`. |
| "Input too long (N tokens)…" | Documents in the conversation plus the question are bigger than the context window. Remove documents or start a new conversation. |
| Port 9002 in use on deploy | Another process holds the port; `start.sh` prints it. It deliberately does not kill processes it did not start. |

# 9. Known Issues and Recommendations

These points were found while reading the code for this document. They are listed so that a new owner knows about them; none has been changed. Each should be confirmed (ideally with a test) before it is fixed.

## 9.1 High priority (security and correctness)

| # | Issue | Where | Impact and suggested fix |
|---|---|---|---|
| 1 | Download ownership check never fails. `is_owner = owner_id == user_id,` has a trailing comma, so `is_owner` is a one-item tuple, which is always truthy. | `document_processor.py`, `download_document` | Any signed-in user can download any document if they know its ID. Remove the comma and add a test. |
| 2 | `/ask` and `/stream` do not check that the user owns an existing `conversation_id`; upload does not check either. | `ChatService.process_message*`, `upload_documents` | A user who knows another conversation's ID can add messages to it and get answers based on its documents. Call `verify_conversation_ownership` before processing. |
| 3 | Files are stored in Ozone under their **bare file name**, while the DB stores `<conv_id>_<filename>` as the key. Chat and download read by bare file name. | `process_upload`, `ChatService`, `download_file` | Two users uploading `report.xlsx` may overwrite or read each other's file (depending on Ozone overwrite behaviour). Store and read using a unique key (for example `<conv_id>/<doc_id>/<filename>`). |
| 4 | The extracted-text copy (`<doc_id>.txt`) is never used. Chat looks for its key in `DESCRIPTION`, which upload leaves NULL, so it reads the **original** file as text. | `get_session_documents`, `process_upload` | For .docx and .xlsx the LLM receives raw ZIP bytes instead of text, so answers about those files are wrong. Store the text key (in DESCRIPTION or a new column) and read it. |

## 9.2 Medium priority (robustness and API behaviour)

- **Upload crashes when every file fails extraction.** `validate_extractions` raises before `extraction_details` is assigned, and the `except` block uses it → 500 instead of the intended JSON. The final `except` after `gather` has a similar problem with `success_count`.
- **Download of an unknown ID gives 500.** `download_document` returns a tuple `(False, {})` which the router then indexes like a dict. Should be 404.
- **`/ask` reports errors with HTTP 200.** Clients and monitoring cannot see failures by status code. Consider proper 4xx/5xx codes.
- **Upload limit is per batch, not per conversation.** Several small uploads can add up to more than the context window; every later question then fails with "Input too long". Count existing `TOKEN_COUNT`s before accepting new files.
- **Deleting a conversation leaves files in Ozone.** Add Ozone deletion (or a clean-up job).
- **Tokenizer is a single point of failure.** Implement the fallback that `TOKENIZE_FALLBACK_ENABLED` suggests (for example a character-based estimate), or fail faster with a clear message.
- **Streaming roll-back is incomplete.** The router always sends a conversation ID to the service, so a failed first question in `/stream` leaves an empty conversation behind; `message_id` in the `complete` event is always null.
- **`auth_router.py` is dead and broken.** Remove it, or redesign it, to avoid someone mounting it by mistake.
- **Full user questions are logged at INFO.** Consider whether this is acceptable for sensitive data; truncate or mask if not.

## 9.3 Housekeeping

- Add a pinned `requirements.txt` (or `pyproject.toml`) and an automated test suite; `test_token_validation.py` is out of date.
- Remove or wire up unused code: `jwt_token.py`, `concurrency.py`, `memory_monitor.py`, `schemas/document.py`, `schemas/user_access.py`, `_trim_history`, unused service helpers.
- Remove unused settings (`API_V1_STR`, `MLFLOW_TRACKING_URI`, `DOCUMENT_MAX_PERCENT`, `USER_QUERY_MAX_TOKENS`) or implement them; every one of them is currently mandatory.
- Either honour or remove the ignored request fields (`temperature`, `max_tokens`, `stream`, `use_context`, `dir`).
- Use one logging approach: `document_router.py` and `document_processor.py` use plain `logging` and `print()`; the rest use `app_logger`.
- Use the shared `DatabaseClient` in `DocumentProcessor` instead of the separate `TeradataClient`.
- Close the HTTP client pools on shutdown (`db_client.close()`, `HttpClient.client`).
- Replace `@app.on_event("startup")` and `Query(regex=...)` with their current FastAPI equivalents (`lifespan`, `pattern=`) to avoid deprecation warnings.
- Move or archive the outdated root `*.md` notes so they are not mistaken for current documentation.
- Add DDL for the three `CD_*` tables to the repository.
